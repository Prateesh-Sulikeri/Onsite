For developers

How Onsite works

Onsite is a Tauri 2 desktop app. The core is Rust; the UI is plain HTML, CSS and JavaScript in the system WebView, with no framework. Everything runs on your machine except the calls to the AI you connect.

One spoken turn

This is the hot path. Everything is tuned so the interviewer starts talking soon after you stop.

  1. Miccpal at the device rate, low-pass filtered, down to 16 kHz mono
  2. VADenergy detector learns the noise floor; your answer ends after your pause setting
  3. Segmentslong answers are cut at short pauses and decoded while you're still talking
  4. Speech to textParakeet gives the live caption; Whisper's text wins when it's there
  5. Clean-uprepeats collapsed, tech terms fixed against a vocabulary
  6. Intervieweranswer + changed workspace + last code run + elapsed time, streamed back
  7. Splittercuts sentences as text streams in; code blocks go to the workspace, never to speech
  8. Text to speechshort sentences batched; the next batch is generated while the current one plays
  9. Speakerwhen playback ends, the mic opens for your next answer

Each answer goes to the interviewer as one message:

Okay, I'd keep a hash map from value to index as I scan.

[Workspace]
Editor (Java):
```
class Solution { ... }
```
[Code run] Run in Java: 2/3 tests passed. First failure: ...
[Elapsed: 14 of 45 min]

The workspace is sent only when it changed since the last turn. The whiteboard is turned into text (shapes, what's inside what, labelled arrows) so the model can read your design.

The AI layer

brain/ hides which AI is in use. It has two entry points: a live Session per round, and run_once for one-shot jobs. Both work on the Claude Code CLI and on four HTTP APIs. There are no provider SDKs, only reqwest.

Claude Code

Each round starts a fresh claude -p process in an empty temp directory, with every way to reach tools or your config turned off:

claude -p --input-format stream-json --output-format stream-json --verbose
  --include-partial-messages --tools "" --setting-sources ""
  --strict-mcp-config --disable-slash-commands
  --system-prompt-file <tmp>/.system-prompt.md --model <model>
  • --tools "" removes every built-in tool. --allowedTools only sets permissions, so it isn't enough.
  • --setting-sources "" keeps your CLAUDE.md and settings out. --disable-slash-commands stops a candidate from reaching an installed skill by saying "/something".
  • The system prompt is fully replaced, not appended. With the coding-agent prompt left in, the model quoted its environment rules back.
  • One process handles every turn of a round: one JSONL user line in, stream events out, ending with a result. If the process dies, the next answer resumes it with --resume.
  • If Claude Code is installed only in WSL, Onsite runs it through wsl.exe -e bash -lc.

Both backends feed the same TurnState, so the UI and voice see the same events either way. One-shot jobs parse their JSON tolerantly: the whole text, else one fenced block, else the first { to the last }.

The interviewer

The interviewer is a prompt, not code. It lives in prompts/interviewer.md and is filled in for each round:

  • Who: a persona from a panel (traits, strictness, backstory, voice), or a name from the catalog.
  • What: the round's guide and rubric, the company style, the level bar, and your resume, job description and notes.
  • Company loops: the dossier's description of that round, with the questions candidates reported.
  • Coding: a problem from the bank, with the optimal complexity, hints to give one at a time, and follow-ups.
  • Variety: Claude Code has no temperature setting, so each round gets a different opener, plus the openings of recent rounds marked "don't reuse".

The prompt asks for 1-4 spoken sentences and one question per turn, no feedback during the round, and pacing by the [Elapsed] tag. When the round is over, the interviewer writes [[END]]. The splitter removes it, and the UI offers "Get my feedback".

Voice

Two engines sit behind one interface (voice/engine.rs):

  • Built-in: Pocket TTS and Parakeet TDT v2 (int8) through the sherpa-onnx crate, on the CPU. The models are pinned GitHub release assets, checked by size and SHA-256, and downloaded only from github.com.
  • VoiceStudio: an external app on 127.0.0.1:3900. Onsite renders a sample line for each panel persona, scores the takes (voiced share, hiss, pitch against the description) and clones the best one, so each persona keeps one stable voice.

Listening

Segments under 3 s are never cut. Between 3 and 20 s they're cut at a 700 ms pause, and past 20 s at 300 ms. Each finished segment is decoded right away, so only the last one is left when you stop. Live captions come from re-decoding the open segment every 500 ms, using at most half the CPU so slow laptops don't drop mic audio.

When the Whisper large-v3 sidecar is ready, each segment also goes to it, with the round's tech vocabulary as the prompt. Its text wins; otherwise Parakeet's is used.

Speaking

Sentences under 4 words wait briefly for the next one and are merged, up to 220 characters. On the built-in engine, long sentences are split at a comma or dash near the middle. That brought first audio on a long reply from 2.5 s to 1.8 s.

Turn-taking

The mic stays closed while the interviewer speaks, since there's no echo cancellation yet. Tapping the orb interrupts: the rest of the reply is dropped from speech but kept in the transcript, and the mic opens. If voice fails at any point, the round carries on typed.

Coding rounds

The question bank is prompts/questions.csv: 81 problems (Blind 75 plus 20 originals), each with typed signatures, tests, hints, follow-ups, a Python reference solution and a stress-test generator. The model only picks the problem; the expected answers are data.

Run uses the example tests. Submit adds the hidden tests and random stress cases checked against the reference. The result goes to the interviewer with your next answer, so it can react to a failing test like a real interviewer would. Lists, trees, graphs, design classes and encode/decode round-trips are all supported.

Comprehension projects

The code comprehension round uses a small multi-file project instead of one problem. You read it in a file tree, edit what you want, and talk through what is wrong. Nothing runs. Your edits go to the interviewer as unified diffs against the original files, so it sees exactly what you changed.

  • Written for you: the AI writes a project from the job posting, the company dossier and your resume. It is checked (2-5 files, safe paths, size limits, 2-4 planted issues with real line numbers, no comments that give a bug away) and sent back once if it fails. Generated code is not compiled or run, so a planted bug can be wrong. Onsite tells you this before the round.
  • Ready-made: eight bundled projects, used when the AI fails twice or you choose them. Each has a ticket-style brief, hidden issues and a reference fix.
  • Graded: the report marks each hidden issue as found, fixed, fixed badly or missed.

Research and dossiers

A research job is the only call that gets tools: web search and web fetch. It runs prompts/research.md as a background task, reads recent candidate reports, and returns a dossier: the rounds, their style, the reported questions, values, pitfalls and sources.

  • Progress is never faked. Search and page counts come from real tool calls in the stream, and stages from PROGRESS lines the model prints.
  • The result is checked against docs/dossier.schema.json and tidied: round names are mapped to round types, and minutes are clamped to 10-180.
  • Dossiers are saved to SQLite and as JSON files, and can be exported and imported.

Feedback

A report needs at least 2 answers and 40 words. The transcript, the metrics (answer lengths, time used, code shares) and the round's rubric go to the report model, with no tools. It returns JSON: an overall score, a decision, rubric scores from 1 to 4 with evidence, what went well, what held you back, "fix first", and better answers for the key moments.

After a full loop, the reports go to a hiring-committee prompt for one verdict and a practice plan. The dashboard is computed in the UI from these reports. It shows no placeholder numbers.

Resume check

The parser reads the file the way an ATS does. The type comes from the bytes, not the file name: PDF (with layout boxes), .docx, .rtf, text and HTML. The checks and the match score are ported from Resume-Matcher (Apache-2.0), and the six ATS profiles follow ats-screener (MIT). This part is deterministic, with no AI.

The AI only reads the job posting to pull out keywords. It then grades the extracted resume text from A to D, the way an AI screen would. The prompt forbids guessing gender or other traits from a name.

Storage and privacy

Everything is stored in one SQLite file (settings, loops, rounds, reports, dossiers, research_jobs) plus a few files in the app data folder. Each turn is saved as it happens, so a crash loses nothing.

  • API keys live in the settings table. They're never sent back to the UI (it only learns whether a key is set) and never logged.
  • No accounts, analytics or telemetry. The network is used only for the AI you picked, research searches, voice model downloads and update checks, the last two only when you ask.
  • Settings has an About page: why Onsite exists, the MIT licence, the author and credits. Its links open fixed pages only (the UI cannot pass a URL to the opener).
  • Storage limits (rounds to keep, days, log size) are enforced at startup. Uninstalling removes the models, log and temp files, and your data too if you choose.

Rules we keep

  1. The interviewer never gets tools. Interviewer, report, verdict and resume calls send none, on every provider. Only research gets web access.
  2. Model output is data. Text from the model and from dossiers is parsed and escaped, never executed.
  3. Bring your own AI. Every feature works on all five providers. Keys come only from Settings.
  4. Speech is local, and never a dead end. Any voice failure falls back to typing.
  5. One live round at a time, one pending reply per round.
  6. Prompts are content. They live in prompts/, not in code. A dev build picks up edits on the next round.

Build and contribute

You need Rust (stable) and the Tauri prerequisites for your system. Then, in src-tauri/:

cargo install tauri-cli --version "^2" --locked
cargo tauri dev                 # run it
cargo clippy -- -D warnings     # before committing
cargo test                      # add -- --ignored to run every reference solution

Each subsystem has a short design doc. Read the one for the area you're changing:
